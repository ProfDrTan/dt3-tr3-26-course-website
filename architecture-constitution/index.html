Architecture Constitution

Four rules for every team's pipeline this trimester. Each one exists because a TR2 team lost real time to the exact mistake it prevents — this page tells you what to do and why, in plain terms, even if this is your first time building something like this.

The Rules

1. Store shared data in GitHub, not in the browser.

Anything your team needs to see across different laptops — scores, logs, sprint data — should be saved as a file in your repo (using the GitHub API, or just committing a file), not saved only inside one person's browser.

WHY — a TR2 team saved their tracker's data only in the browser. The moment a teammate opened it on a different laptop, it looked empty — the data never actually left the first machine. Saving to the repo means everyone sees the same thing, automatically.
2. If your dashboard is private-repo data shown in a public webpage, publish the data first.

A webpage running in someone's browser can't hold a secret login. If your dashboard needs data from a private repo, have a scheduled script copy that data out to a public file first — then have the dashboard read the public file, not the private repo directly.

WHY — a TR2 dashboard tried to read straight from a private repo with no login, which just fails silently. Numbers looked frozen for days before anyone noticed nothing was actually updating.
3. Name your automated pipeline file the same thing every team uses: main-pipeline.yml.

If you're using GitHub Actions to automate something, the file that runs it goes in .github/workflows/ and is named exactly main-pipeline.yml — whatever you call the pipeline yourself internally.

WHY — TR2 teams each picked their own name, which made it impossible to glance across five teams and tell who was actually running automation and who wasn't. One name means one place to look, every time.
4. A green checkmark doesn't prove anything actually happened.

If you automate a task, add a step that checks something real actually changed (a new row, a new file, an updated timestamp) — don't just trust that "the job finished with no errors" means it did its job.

WHY — a TR2 pipeline passed its checks every single week while quietly never saving any new data, for weeks, because "ran without error" and "actually did the work" turned out to be two very different things.

What This Means Day-to-Day

  • Your team's repo lives under the cp3405-tr3-2026 GitHub organization, not a personal account — commit history can't be rewritten or backdated, so your commit record actually means what it says.
  • Before saving anything your teammates need to see, ask: "is this only in my browser, or is it in the repo?" If it's only in your browser, move it to the repo.
  • Before your dashboard fetches anything, ask: "is this path public, or would this call fail with no login?" If it would fail, publish the data first.
  • Name your CI file main-pipeline.yml from the very first commit — renaming it later just means old runs vanish from the history you can point to.
  • Your Sprint 2 submission should already include an output-verification step, not bolt one on later.
